# README 작성 실행 계획

## 목표

OOTP Milestone Tracker를 처음 접한 사용자가 README만으로 다음 내용을 이해하고 실행할 수 있도록 합니다.

- 프로그램이 제공하는 기능
- 설치 또는 실행 방법
- OOTP에서 준비해야 할 데이터
- 앱의 최초 설정 방법
- 기록을 가져오고 확인하는 전체 사용 순서
- 각 화면의 역할과 다음 작업
- 반복 사용과 데이터 갱신 방법

README는 기능 목록만 제공하는 소개 문서가 아니라 **설치부터 첫 결과 확인까지 안내하는 사용자용 시작 문서**로 작성합니다.

### GPT — 총괄 및 최종 편집

- 조사 작업 분배
- 기능 설명의 우선순위 결정
- 코드·UI·문서 간 충돌 해결
- README 전체 구조 작성
- 사용자 관점 최종 검수
- PR 변경 범위 관리

### Codex — 저장소 조사와 검증

- 실제 UI 탭과 버튼 조사
- 기능별 코드 경로 확인
- 설치·실행·테스트·빌드 명령 검증
- 데이터 import 파일명과 경로 확인
- 설정 저장 위치와 세이브별 DB 동작 확인
- 확인 근거를 파일 단위로 정리

### Claude — 문장과 사용 설명 보완

- 동일한 개념의 용어와 문체 통일

Claude는 필수 담당이 아니며, GPT가 문장 품질을 충분히 확보하면 생략할 수 있습니다.

## 작업 단계

## 1단계. 현재 상태 고정

확인 대상:

- 현재 버전
- 기본 브랜치와 최신 커밋
- 기존 README와 사용자 문서
- 설치 방식과 배포본 존재 여부
- 실제 UI 탭 목록

산출물:

- 현재 상태 요약
- 오래되었거나 서로 충돌하는 문서 목록
- 추가 확인이 필요한 항목

완료 기준:

- README가 어떤 버전의 앱을 설명하는지 확정됨

## 2단계. 기능 인벤토리 작성

기능을 다음 단위로 조사합니다.

1. 대시보드
2. 달성 기록
3. 선수 기록
4. 기록 달성 예측
5. 연속 기록 센터
6. 기존 기록 가져오기
7. 레이팅 편집
8. 설정
9. 수동 이벤트 입력
10. 한글 이름 매핑
11. 세이브별 DB와 데이터 관리

각 기능에 대해 다음 표를 작성합니다.

| 항목 | 내용 |
|---|---|
| 사용자 목적 | 사용자가 이 기능으로 해결하는 문제 |
| 진입 화면 | 실제 UI 탭·버튼 이름 |
| 필요한 입력 | 파일, 설정, 선수 또는 팀 선택 |
| 주요 조작 | 사용자가 수행하는 행동 |
| 결과 | 화면이나 DB에 반영되는 내용 |
| 제한 사항 | 미지원 또는 주의가 필요한 흐름 |
| 검증 근거 | 코드·테스트·문서 경로 |

완료 기준:

- README의 모든 기능 설명에 검증 근거가 존재함
- 내부 구현 용어가 아닌 사용자 행동 중심으로 정리됨

## 3단계. 전체 사용 흐름 검증

최초 사용 흐름을 실제 순서대로 검증합니다.

```text
1. 프로그램 설치 또는 실행
2. OOTP에서 stats 및 box score 데이터 준비
3. 앱에서 OOTP 경로 설정
4. 현재 시즌과 추적 팀 설정
5. 기존 선수 기록 가져오기
6. 박스스코어 가져오기
7. 대시보드와 기록 화면에서 결과 확인
8. 필요 시 수동 이벤트 추가
9. 시즌 중 새 경기 반복 반영
10. 시즌 종료 후 stats 갱신
```

각 단계에서 확인할 내용:

- 정확한 UI 이름
- 필요한 파일명
- 성공 여부를 판단하는 화면
- 사용자가 흔히 막힐 수 있는 조건
- 다음 단계로 연결되는 방법

완료 기준:

- 신규 사용자가 별도 개발 문서 없이 첫 import를 완료할 수 있음

## 4단계. README 정보 구조 확정

권장 목차:

```text
프로젝트 소개
대표 화면
이 프로그램으로 할 수 있는 일
주요 기능
설치 및 실행
OOTP 데이터 준비
처음 사용하는 순서
화면별 사용법
반복 사용 및 시즌 갱신
데이터 저장 위치와 백업
자주 발생하는 문제
개발자용 테스트와 빌드
상세 문서
```

구조 원칙:

- 기능 소개는 상단에 둡니다.
- 설치와 OOTP 데이터 준비를 분리합니다.
- 전체 사용 순서는 기능 목록보다 구체적으로 작성합니다.
- 개발자 정보는 사용자 안내 뒤에 둡니다.
- 상세 규칙은 `docs/`로 연결하고 README 본문에 중복하지 않습니다.

완료 기준:

- 사용자가 필요한 정보를 목차에서 바로 찾을 수 있음

## 5단계. 스크린샷 계획 및 준비

최소 권장 세트:

1. 대시보드 — 앱 전체 기능 요약
2. 선수 기록 — 핵심 조회 흐름
3. 기록 달성 예측 — 차별화 기능

추가 후보:

- 달성 기록
- 연속 기록 센터
- 기존 기록 가져오기
- 설정

각 이미지마다 정할 항목:

- 파일명
- 촬영할 탭
- 표시할 샘플 데이터
- 선택된 필터
- README 삽입 위치
- 가려야 할 개인정보

자동 촬영 기반이 없으면 수동 촬영 계획을 먼저 확정하고, 이미지가 실제 추가되기 전에는 깨진 링크를 README에 넣지 않습니다.

완료 기준:

- 각 이미지의 목적과 촬영 상태가 문서화됨

## 6단계. README 초안 작성

초안 작성 규칙:

- 한 줄 소개에서 입력 데이터와 결과를 함께 설명합니다.
- 주요 기능마다 사용자가 얻는 결과를 먼저 작성합니다.
- 처음 사용하는 순서는 번호 목록으로 작성합니다.
- 파일명, 버튼명, 경로는 코드 표기합니다.
- 중요한 제한은 관련 단계 바로 아래에 둡니다.
- 추측한 설명은 작성하지 않습니다.

완료 기준:

- README만 읽고 프로그램 목적, 기능, 설치, 첫 사용 흐름을 설명할 수 있음

## 7단계. 기술 검증

검증 항목:

- `git clone`과 가상환경 명령
- Python 버전과 패키지
- 설정 파일 생성 방법
- `python main.py`
- `pytest`
- `python build.py`
- OOTP import 파일명과 경로
- 앱 데이터 저장 위치
- 세이브별 DB 분리
- 모든 내부 Markdown 링크

가능한 경우 실제 명령을 실행해 확인합니다. 실행할 수 없는 항목은 코드와 CI 또는 테스트를 통해 확인하고 그 한계를 기록합니다.

완료 기준:

- README에 존재하지 않는 명령이나 기능이 없음

## 8단계. 사용자 관점 검수

다음 질문으로 최종 검수합니다.

- OOTP를 아는 일반 사용자가 개발 용어 없이 이해할 수 있는가?
- 설치 직후 무엇을 해야 하는지 분명한가?
- 어떤 OOTP 파일이 필요한지 한곳에서 확인 가능한가?
- 각 기능을 어느 화면에서 사용하는지 알 수 있는가?
- 최초 사용과 이후 반복 사용이 구분되어 있는가?
- 실패 가능성이 높은 조건이 관련 단계에 적혀 있는가?
- 기능 소개와 실제 UI 명칭이 일치하는가?

완료 기준:

- 위 질문에 모두 예라고 답할 수 있음

## 9단계. PR 검토와 반영

PR에는 다음을 포함합니다.

- README 변경 요약
- 검증한 명령과 기능 범위
- 추가 또는 갱신한 스크린샷
- 아직 확인되지 않은 항목
- 후속 문서 작업

병합 전 확인:

- Markdown 렌더링
- 이미지와 링크
- 오탈자와 용어 통일
- 최신 브랜치와의 충돌

## README 핵심 완료 조건

최종 README는 최소한 다음 질문에 직접 답해야 합니다.

### 기능

- 어떤 기록을 자동으로 추적하는가?
- 연속 기록과 예측 기능은 무엇인가?
- 수동으로 어떤 이벤트를 추가할 수 있는가?
- 선수 기록, 레이팅 편집, 한글 이름 매핑은 어디서 사용하는가?

### 사용법

- 프로그램을 어떻게 설치하고 실행하는가?
- OOTP에서 어떤 파일을 준비하는가?
- 처음 실행 후 어떤 설정을 하는가?
- 어떤 순서로 데이터를 가져오는가?
- 결과는 어느 화면에서 확인하는가?
- 다음 경기와 다음 시즌에는 무엇을 반복하는가?

이 두 영역이 충분히 설명되지 않으면 README 작업은 완료로 판단하지 않습니다.
