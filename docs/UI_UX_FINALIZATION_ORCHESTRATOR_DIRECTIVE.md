# OOTP Milestone Tracker UI/UX 최종 마감 오케스트레이터 지시서

## 1. 문서 지위와 목적

이 문서는 `codex/ui-ux-audit-improvements` 브랜치의 UI/UX 전면 개선을 **실제 사용 가능한 최종 상태**까지 마무리하기 위한 최상위 후속 지시서다.

기존 `UI_UX_ORCHESTRATOR_DIRECTIVE.md`가 화면 구조와 1차 구현 범위를 정의했다면, 이 문서는 1차 구현 후 검수에서 발견된 **기능 연결 누락, 정적 상태 표시, 내부값 노출, 검증 과장**을 수정한다.

- 대상 브랜치: `codex/ui-ux-audit-improvements`
- 현재 기준 커밋: `1939ee44576a8a26a022b63f1a50a7726a1f96a8`
- 선행 지시서: `docs/UI_UX_ORCHESTRATOR_DIRECTIVE.md`
- 감사 기준: `docs/OOTP_Milestone_Tracker_UI_UX_Audit.md`
- 현재 구현 보고서: `docs/UI_UX_IMPLEMENTATION_REPORT.md`
- 이 문서는 위 문서들의 후속 마감 기준이며, **충돌 시 이 문서가 우선한다.**

현재 브랜치는 UI 골격과 주요 화면 개편은 구현됐지만 다음 이유로 최종 완료가 아니다.

1. 통합 가져오기 5단계가 실제 백엔드 상태와 연결되지 않았다.
2. 대시보드 작업 상태가 실제 실행 결과가 아니라 경로 존재 여부 또는 고정값에 의존한다.
3. 메시지 `다시 분석`, 기존 반영 감지, 결과별 이동 기능이 실제로 연결되지 않았다.
4. 메시지 유형·제외 이유·추출 필드에 내부 영어 코드가 노출된다.
5. 수동 입력과 자동 추출 수정이 같은 안내형 폼을 재사용하지 않는다.
6. 기존 메시지 자동 기록의 출처 마이그레이션이 `manual`로 잘못 분류될 수 있다.
7. offscreen PNG 생성은 실제 Windows 125% DPI 검증을 대체하지 못한다.
8. GitHub CI 근거 없이 로컬 테스트 결과만으로 완료가 선언됐다.

오케스트레이터는 이 문서를 읽은 뒤 기존 구현을 폐기하지 말고, 위 결함을 수정해 **실제 사용 흐름과 보고서의 주장 사이를 일치**시켜야 한다.

## 2. 최종 목표

최종 결과는 다음 사용자 흐름이 끊김 없이 동작해야 한다.

1. 사용자가 대시보드에서 현재 데이터 상태와 다음 작업을 확인한다.
2. `기록 가져오기`에서 박스스코어·뉴스 메시지·통산 기록 중 작업을 선택한다.
3. 각 작업은 원본 확인 → 분석 → 검토 → 저장 → 결과 확인 단계로 실제 진행한다.
4. 뉴스 메시지는 저장 전에 후보·제외·날짜 누락·오류·기존 반영 상태를 확인한다.
5. 사용자가 추출 결과를 자연어 폼으로 수정하거나 날짜를 보완한다.
6. 승인된 항목만 저장되고, 결과 화면에서 생성·중복·제외·오류를 구분한다.
7. 달성 기록에서 출처와 원문 근거를 확인한다.
8. 다시 같은 메시지를 스캔해도 기존 반영 항목이 후보로 오인되지 않는다.
9. 한국어 모드에서 내부 enum·클래스명·필드명·오류 코드가 노출되지 않는다.
10. Windows 125% 배율과 최소 창에서 주요 기능에 접근할 수 있다.

## 3. 오케스트레이터 운영 규칙

### 3.1 역할

오케스트레이터는 직접 모든 구현을 한꺼번에 수행하지 않는다.

- 저장소 상태 분석
- 작업 순서와 의존성 결정
- 에이전트별 파일 소유권 지정
- 구현 결과 검수
- 교차 기능 통합
- 회귀 테스트
- 실제 화면 검증
- 최종 완료 판정

을 담당한다.

### 3.2 모델 배분

- GPT-5.6 Sol: 전체 계획, 파일 소유권, 통합, 최종 검증
- GPT-5.5: 데이터 모델·상태 저장·테스트 또는 독립 검수
- Sonnet 5: GUI 구현·현지화·폼 재사용 또는 독립 검수

GPT-5.5와 Sonnet 5의 실제 구현량을 가능한 한 균형 있게 배분한다. 한 모델이 제한으로 작업하지 못하면 오케스트레이터가 즉시 재배정하되, 보고서에 실제 담당 결과를 기록한다.

### 3.3 중간 보고

차단 요인이 없으면 중간 설명을 길게 작성하지 않는다.

차단 시에만 다음 형식으로 보고한다.

- 차단 요인
- 필요한 결정
- 영향 파일
- 권장 처리

정책 변경이 아닌 구현 세부사항은 사용자에게 묻지 말고 기존 지시와 코드 구조를 기준으로 결정한다.

### 3.4 파일 소유권

같은 파일을 여러 에이전트가 동시에 수정하지 않는다.

각 작업을 시작하기 전에 다음 표를 만든다.

| 작업 ID | 담당 모델 | 소유 파일 | 읽기 전용 참조 | 수정 금지 | 선행 작업 | 완료 조건 |
|---|---|---|---|---|---|---|

공통 파일은 오케스트레이터가 순차 병합한다.

### 3.5 완료 선언 금지

다음만으로 완료 처리하지 않는다.

- 위젯이 존재함
- 버튼이 보임
- 단위 테스트가 통과함
- offscreen PNG가 생성됨
- 문서에 완료라고 적힘

각 기능은 실제 사용자 동작, 상태 변화, DB 결과, 재실행 결과까지 검증한다.

# Phase F1 — 실제 가져오기 상태 모델과 작업 연결

## F1-1. 영구 작업 상태 저장

현재 대시보드는 경로 존재 여부와 단일 `last_import_at`에 의존한다. 다음 작업별 상태를 별도로 저장한다.

- `latest_boxscores`
- `news_messages`
- `baseline_history`
- `season_finalize`

권장 저장 위치는 기존 `settings.import_state`의 구조 확장 또는 별도 `import_runs` DB 테이블이다. 기존 설정과 호환되고 테스트하기 쉬운 방식을 선택한다.

각 작업은 최소 다음 값을 가진다.

- 마지막 시작 시각
- 마지막 완료 시각
- 마지막 결과: 완료 / 부분 성공 / 실패 / 취소
- 현재 단계
- 처리 수
- 생성 수
- 중복 수
- 제외 수
- 날짜 누락 수
- 오류 수
- 결과 상세 또는 보고서 참조

### 완료 조건

- 앱 재실행 후에도 마지막 작업 상태가 유지된다.
- 서로 다른 가져오기 작업이 같은 `last_import_at`을 덮어쓰지 않는다.
- 취소와 실패가 완료로 표시되지 않는다.

## F1-2. 공통 상태 머신 구현

표시용 5단계 목록만 두지 말고 실제 상태 전이를 구현한다.

상태:

1. `source_check`
2. `analyze_classify`
3. `review_results`
4. `save`
5. `confirm_result`

종료 상태:

- `completed`
- `partial_success`
- `failed`
- `cancelled`

각 작업 엔진이 모든 내부 구현을 공유할 필요는 없지만, UI에 제공하는 상태 계약은 하나로 통일한다.

권장 인터페이스 예시:

```python
@dataclass
class ImportWorkflowState:
    workflow_id: str
    current_step: str
    outcome: str | None
    totals: dict[str, int]
    unresolved: dict[str, int]
    started_at: str | None
    completed_at: str | None
    message: str
```

### 완료 조건

- 단계 버튼이 실제 현재 상태와 동작에 따라 활성화된다.
- 분석하지 않은 작업에서 저장 버튼이 실행되지 않는다.
- 검토가 필요한 작업은 검토 완료 전 저장되지 않는다.
- 결과 확인 단계에서 처리 결과가 페이지에 유지된다.

## F1-3. 가져오기 카드 동작 라우팅

현재는 카드의 어느 단계 버튼을 눌러도 같은 동작이 실행된다. 이를 수정한다.

### 최신 경기

- 원본 확인: 폴더·신규 파일·변경 파일 수 확인
- 분석/저장: 실제 박스스코어 가져오기 실행
- 검토: 새 기록·오류 요약
- 결과: 기록 또는 오류 화면으로 이동

### 뉴스 메시지

- 원본 확인: 탐색 경로와 파일 수 확인
- 분석: 메시지 파싱 및 기존 반영 감지
- 검토: 검토 화면 열기
- 저장: 승인 항목만 저장
- 결과: 저장·중복·제외·오류 요약

### 통산·과거 시즌

- 원본 확인: 필수 파일 존재와 날짜 확인
- 분석: 비교 실행
- 검토: 차이 화면
- 저장: 기존 importer 실행
- 결과: 반영·미반영·오류 요약

### 완료 조건

- 각 단계 버튼이 다른 목적을 수행한다.
- `open:*` 보조 링크도 단계별 목적지로 이동한다.
- 결과 요약의 `기록 보기`, `검토 필요`, `오류 보기`가 서로 다른 대상 화면/필터를 연다.

# Phase F2 — 대시보드 상태를 실제 데이터와 연결

## F2-1. 6단계 상태 계산

다음 상태를 실제 데이터로 계산한다.

### 1. 세이브와 추적 팀

- 세이브 선택 여부
- 추적 팀 설정 여부
- 경로 접근 가능 여부

### 2. 통산 초기값

- 단순 폴더 존재가 아니라 실제 초기 기록 적재 여부
- 적재 시즌 및 마지막 완료 시각
- 현재 시즌 대비 갱신 필요 여부

### 3. 최신 박스스코어

- 신규 또는 변경된 파일 수
- 마지막 성공/부분 성공/실패 결과
- 가져오기 진행 중 상태

### 4. 뉴스 메시지

- 전체 메시지 수
- 미처리 메시지 수
- 날짜 누락·오류 수
- 마지막 검토·저장 결과

### 5. 미처리 항목

- 박스스코어 오류
- 뉴스 날짜 누락
- 파싱 오류
- 승인 대기
- 비교 충돌

### 6. 시즌 종료 판정

- 시즌 종료 여부를 확실히 알 수 없다면 자동 완료로 추정하지 않는다.
- 마지막 시즌 최종 판정 실행 시각과 시즌을 표시한다.
- 현재 시즌과 일치하지 않으면 `필요`로 표시한다.

## F2-2. 다음 행동 정확성

각 단계의 주 행동은 상태에 따라 달라야 한다.

예:

- 폴더 없음 → 설정 열기
- 신규 파일 있음 → 가져오기 실행
- 분석 완료·승인 대기 → 검토 열기
- 날짜 누락 있음 → 날짜 누락 필터 열기
- 오류 있음 → 오류 목록 열기
- 모두 완료 → 결과 보기

### 완료 조건

- 작업 후 대시보드 상태가 즉시 바뀐다.
- 앱 재실행 후에도 동일 상태가 유지된다.
- 고정된 `필요` 문구가 남아 있지 않는다.

# Phase F3 — 뉴스 메시지 검토 기능 완성

## F3-1. 다시 분석 실제 연결

현재 `reanalyze_callback`이 앱에서 제공되지 않는다. 실제 파서를 다시 호출하도록 연결한다.

재분석 시 유지/초기화 규칙:

- 원문과 source ID 유지
- 사용자가 수동 수정한 값은 재분석 전에 확인
- 재분석 결과로 후보·제외·날짜 누락·오류 상태 갱신
- 이미 저장된 항목은 다시 후보가 되지 않음

### 완료 조건

- 원문 수정 또는 파서 변경을 가정한 테스트에서 결과가 실제 갱신된다.
- 콜백이 없는 무동작 버튼이 존재하지 않는다.

## F3-2. 기존 반영 감지

메시지 스캔 시 DB를 조회해 다음을 판별한다.

- 이미 반영된 source ID
- 일부 폼만 반영된 메시지
- 동일 source ID의 중복 기록
- 사용자가 과거에 제외한 메시지

가능하면 `processed_messages` 또는 이에 준하는 명시적 테이블을 도입한다.

권장 필드:

- source ID
- 원본 경로
- 파일 수정 시각 또는 해시
- 처리 상태
- 생성 기록 ID 목록
- 제외 사유
- 마지막 처리 시각

기존 `notes`의 `source:<id>`는 마이그레이션과 호환 조회에 사용하되, 새 구현의 유일한 상태 저장소로 사용하지 않는다.

### 완료 조건

- 저장 후 다시 스캔하면 `이미 반영됨`으로 표시된다.
- 이미 반영된 항목은 `전체 승인` 대상이 아니다.
- 원본 파일이 변경된 경우 `변경됨·재검토 필요`로 구분할 수 있다.

## F3-3. 저장 결과의 행별 연결

현재 하나의 저장 결과 ID 목록이 모든 적용 항목에 복사될 수 있다. 각 메시지와 생성 기록 ID를 정확히 연결한다.

저장 콜백 결과는 다음처럼 메시지별 결과를 반환한다.

```python
@dataclass
class MessageApplyResult:
    source_id: str
    created_record_ids: list[int]
    duplicate_record_ids: list[int]
    errors: list[str]
```

### 완료 조건

- 각 행에서 자신이 생성한 기록만 확인된다.
- 중복 때문에 새 기록이 없으면 `중복·기존 반영`으로 표시된다.
- 일부 메시지 실패가 전체 성공으로 표시되지 않는다.

## F3-4. 검토 화면 필터

최소 다음 필터 또는 빠른 이동을 제공한다.

- 전체
- 후보
- 승인됨
- 날짜 필요
- 제외
- 이미 반영됨
- 오류

결과 요약의 버튼은 이 필터 상태를 연다.

# Phase F5 — 수동 입력과 자동 추출 수정 폼 통합

## F5-1. 공통 안내형 폼 컴포넌트

다음 유형별 공통 폼을 만든다.

- 마일스톤/수상
- 팀 이동/계약
- 부상

각 폼은 두 입력 경로에서 재사용한다.

1. 수동 기록 추가
2. 메시지 자동 추출 결과 수정

공통 동작:

- 선수 자동완성
- 팀 선택
- 날짜 선택기
- 시즌 자동 계산
- 필수값 표시
- 유형별 입력 검증
- 저장 전 미리보기

## F5-2. 내부 필드 편집 제거

메시지 수정 시 사용자에게 dataclass 전체 필드를 표로 직접 편집하게 하지 않는다.

- ID는 이름 선택으로 처리
- milestone key는 사용자 기록명 선택으로 처리
- 날짜는 날짜 선택기 사용
- 숫자는 범위·단위 표시
- 필요 없는 필드는 숨김

기술 지원을 위해 원시 편집을 남겨야 한다면 `고급 원시 편집`으로 접고 기본 경로에서는 숨긴다.

## F5-3. 일괄 입력 유지

수동 기록 일괄 표 입력은 보조 기능으로 유지한다.

- 기본 모드는 개별 폼
- 일괄 모드는 명시적으로 전환
- 행별 오류 표시
- 저장 가능 건수 표시
- 유형별 필수 열만 표시

### 완료 조건

- 메시지 수정과 수동 입력이 같은 검증 함수를 사용한다.
- 사용자에게 내부 필드명이 기본 노출되지 않는다.
- 동일 입력값이 두 경로에서 동일한 DB 결과를 만든다.

# Phase F6 — 기존 데이터 출처 마이그레이션 보완

## F6-1. 메시지 자동 기록 추론

현재 기존 `is_manual=1` 기록을 모두 `manual`로 분류할 수 있다. 다음 신호를 우선 사용해 `message_auto`를 추론한다.

1. `notes`에 `source:<message-id>` 존재
2. 알려진 메시지 자동화 milestone key/description 패턴
3. processed message 상태와 연결 가능
4. 그 외 `is_manual=1`은 `manual`

마이그레이션은 반복 실행해도 결과가 변하지 않아야 한다.

## F6-2. 불확실한 기록

자동·수동을 확정할 수 없는 기록을 무리하게 `message_auto`로 바꾸지 않는다.

선택 가능한 정책:

- `migration`으로 유지
- 별도 마이그레이션 로그에 기록

사용자 화면에서는 `이전 데이터`로 표시한다.

## F6-3. 마이그레이션 보고

최초 실행 시 로그 또는 고급 도구에서 다음 수를 확인할 수 있게 한다.

- 박스스코어 자동으로 분류
- 뉴스 자동으로 분류
- 수동으로 분류
- 시즌 최종 판정으로 분류
- 불확실/이전 데이터

### 완료 조건

- 기존 메시지 자동 기록 fixture가 `message_auto`로 마이그레이션된다.
- 기존 일반 수동 기록은 `manual`로 유지된다.
- 새 DB와 기존 DB 모두 테스트된다.

# Phase F7 — 반응형·DPI·실제 화면 검증

## F7-1. 자동 검증의 한계 수정

현재 캡처 검증은 PNG 크기와 파일 존재만 확인한다. 보고서에서 이를 `잘림 검증 완료`로 표현하지 않는다.

자동 검증은 다음만 증명한다고 명시한다.

- 화면 생성 성공
- 지정 픽셀 크기 렌더링
- 주요 위젯 존재
- 예외 없음

## F7-2. 구조적 레이아웃 검사

가능한 범위에서 다음을 자동 검사한다.

- 필수 위젯 geometry가 부모 영역 밖으로 나가지 않음
- 주요 버튼이 visible/enabled 상태
- 기본 필터와 표의 핵심 열 접근 가능
- 최소 창에서 가로 오버플로가 없음
- 스크롤이 필요한 페이지는 스크롤 영역 존재
- 한국어/영어 긴 문자열용 minimum size 또는 word wrap 적용

## F7-3. 실제 Windows 검증

최종 완료를 위해 Windows 데스크톱에서 다음 조합을 검증한다.

- 1650×900 / 100%
- 1366×768 / 125%
- 앱 최소 크기 / 125%
- 한국어
- 영어

검증 화면:

1. 대시보드
2. 달성 기록 기본
3. 고급 필터 펼침
4. 기록 상세
5. 기록 가져오기
6. 뉴스 메시지 검토
7. 날짜 누락 필터
8. 완료·부분 성공·오류 결과
9. 수동 기록 개별 입력
10. 연속 기록
11. 설정
12. 고급 도구

각 화면에서 확인:

- 텍스트 잘림
- 겹침
- 비정상 빈 공간
- 포커스 이동
- 버튼 접근성
- 스크롤 가능 여부
- 한글 폰트 렌더링

## F7-4. 사용자 확인이 필요한 경우

오케스트레이터 실행 환경에서 실제 Windows 125% 확인이 불가능하면, 이를 완료로 처리하지 않는다.

대신 다음을 준비한 뒤 사용자에게 한 번만 요청한다.

- 자동 실행 가능한 검증 스크립트
- 확인할 화면과 조작 순서
- 스크린샷 저장 경로
- 통과/실패 체크리스트

중간 단계가 아닌 **최종 사용자 검수 단계에서만** 요청한다.

## 9. 최종 완료 조건

다음 항목을 모두 충족해야 완료다.

- 통합 가져오기 5단계가 실제 상태 변화와 연결됨
- 단계별 버튼과 결과 버튼이 올바른 동작/화면으로 이동함
- 대시보드가 실제 작업 상태를 표시함
- 작업 상태가 앱 재실행 후 유지됨
- 메시지 다시 분석이 실제로 동작함
- 기존 반영 메시지가 스캔 단계에서 구분됨
- 메시지별 생성·중복·오류 결과가 정확히 연결됨
- 한국어 UI에 내부 category/reason/class/field 코드가 남지 않음
- 수동 입력과 자동 추출 수정이 공통 안내형 폼을 사용함
- 기존 메시지 자동 기록이 `message_auto`로 올바르게 마이그레이션됨
- 전체 테스트 통과
- CI 또는 재현 가능한 실행 증거 존재
- Windows 125% 검증 완료 또는 사용자 최종 검수만 명확히 남음
- 최종 구현 보고서가 완료·부분 완료·미구현을 사실대로 구분함

## 10. 최종 완료 금지 조건

다음 중 하나라도 남으면 `UI/UX 전면 개선 완료`로 보고하지 않는다.

- 가져오기 단계가 단순 안내 라벨임
- 대시보드 뉴스/오류/시즌 상태가 고정값임
- 다시 분석 버튼이 무동작임
- 저장한 메시지가 다시 후보로 나타남
- 결과 버튼이 모두 같은 화면으로 이동함
- 메시지 유형이나 제외 이유가 내부 코드로 표시됨
- 메시지 수정에서 dataclass 필드를 직접 편집해야 함
- 기존 뉴스 자동 기록이 수동으로 마이그레이션됨
- PNG 존재만으로 DPI 검증 완료라고 주장함
- GitHub CI나 재현 가능한 테스트 근거가 없음
- 실제 Windows 확인이 안 됐는데 잘림 없음으로 보고함
